# CRISP-DM log

## Business Understanding
- **Idea selection**: Considered a Ukrainian "Granola" (meeting notes), a lecture companion, a writing assistant, and a voice-note inbox. *Why the inbox:* high daily use for the owner, short inputs make gold labelling cheap (every component can be evaluated), and it is more than plain RAG (segmentation, classification, extraction, date resolution, linking, clarification). *Evidence:* assignment PDF criteria (evaluation 4 pts, per component).
- **Local-only, menu-bar app**: All models run locally (Ollama + Parakeet); the interface is a macOS menu-bar app plus a web dashboard. *Why:* the owner wants a free personal replacement for paid tools, and real notes are private. *Evidence:* M4 Pro / 24 GB can run 12–14B models.
- **Success criteria**: A note's items are useful if type, title, and date are correct without edits. Headline metric: share of notes where every item is fully correct (target ≥0.6).

## Data Understanding
- **TypeWhisper history**: 412 dictations (Sep 3 – Nov 9, 2026), 96 contain Ukrainian. Average ~46 words / ~29 s, close to real inbox notes. Only 3 Ukrainian records still have audio, so they're unusable for ASR evaluation. Many are prompts or messages, not to-dos. *Decision:* use them as a private, text-only real-world check for C3–C7. *Evidence:* `scripts/export_typewhisper.py`.

- **Public datasets**: SLURP (spoken commands) is English-only. MASSIVE is multilingual, but Ukrainian coverage is still to be verified, and both are single-intent commands rather than multi-item notes with relative dates. *Decision:* build a scripted gold set. *Evidence:* see Data Preparation.

## Data Preparation
- **Scripted gold set**: 63 notes / 84 items (43 task, 28 event, 7 idea, 6 note) in `data/scripted/scripts.jsonl`, built by `data/scripted/build_scripts.py` with written labelling conventions (bare weekday = next occurrence strictly after today; "наступн* <weekday>" = next calendar week; hours 1–7 = PM; зранку 09:00, після обіду 14:00, ввечері 19:00). Gold datetimes are explicit and checked by code for weekday consistency. *Why:* reproducible labels and cheap per-component evaluation. *Evidence:* `uv run python -m eval.validate_data`.
- **Labelling pitfall found by the checker**: naive weekday matching mislabels "понеділок" as Sunday ("неділ" substring) and "о четвертій" (4 o'clock) as Thursday. The checker was fixed, and the same cases became unit tests for C5.

## Modeling
- **Component split**: C3 (segment + classify) and C4 (extract) are separate LLM calls so errors can be attributed; C5 and C7 are rules (deterministic, testable), with the LLM only as a date fallback with whole-note context (e.g. "за два дні до того"). *Why:* evaluation per component is graded, and rules are more reliable than a 12B model for date arithmetic.
- **Local models**: Ollama `gemma3:12b` (default) vs `qwen3:14b` (comparison), structured JSON output via the schema in `format`, temperature 0, 1 retry. ASR is Parakeet TDT v3 via `parakeet-mlx`. Embeddings are `multilingual-e5-small`.

- **Eval audio recorded**: the owner recorded 62/63 scripted notes (6.0 min, 16 kHz mono, MacBook mic); 1 skipped (n017, phrasing felt unnatural). Slight paraphrasing while reading was allowed. The recorder got a level check, playback, and skip; `scripts/check_recordings.py` summarises coverage. *Evidence:* `data/scripted/audio/` (not committed).

## Evaluation
- **C5 dates on the gold set**: 43/44 exact (0.977) after fixing two Ukrainian morphology gaps found by unit tests ("пів на **третю**" ends in -ю; "**третього**" ends in -ього). The 1 miss is "за два дні до того", which needs whole-note context and goes to the LLM fallback. *Caveat:* the rules were developed against this set, so the score is optimistic. *Evidence:* `eval/results/c5.md`.
- **C5 held-out check**: 30 new phrases written before running the rules on them. Rules only: 27/30 (0.90). Misses: "через пів години" (dateparser drops the time), "на вихідних", "третього числа" (no rule). *Decision:* report them as known gaps; any later fix is logged separately because it makes the set no longer held-out. *Evidence:* `data/scripted/dates_heldout.jsonl`, `eval/results/c5_heldout.md`.
- **C8 store/export**: 84/84 items round-trip exactly through SQLite; 44/44 dated items produce valid `.ics` files with the correct DTSTART. *Evidence:* `eval/results/c8.md`.
- **C3 segment + classify (gemma3:12b, gold text)**: item-count accuracy 0.968, segmentation F1 0.964, type macro-F1 0.978 (task↔event confusions: 2 tasks → event, 1 event → task). ~3.9 s/note. *Evidence:* `eval/results/c3.md`.
- **C4 extraction (gemma3:12b)**: on 81 aligned items: title match 0.963, date-phrase token-F1 0.943, people F1 0.907, unresolved-pronoun accuracy 0.988. *Evidence:* `eval/results/c4.md`.
- **C7 follow-up questions**: precision 1.0, recall 0.875 (7/8 incomplete items asked about, no false questions). *Evidence:* `eval/results/c7.md`.
- **C6 project linking: embeddings rejected, LLM adopted**: multilingual-e5-small reached only 0.595 accuracy at the best threshold (0.84). All item–project similarities fall in 0.82–0.86, so the model cannot separate "which project" from "no project". Letting gemma3:12b choose from the fixed project list (enum-constrained JSON) gives 0.798. Remaining errors are mostly items gold-labelled `null` that the LLM puts in a plausible project (gift for mom → Дім, презентація → Робота), which points to **label ambiguity**: the "no project" rule wasn't written precisely. *Decision:* the pipeline uses the LLM; embeddings stay for dedup. *Evidence:* `eval/results/c6.md`.
- **C6 dedup threshold**: F1 rises from 0.16 (cosine 0.86) to 0.80 (0.96–0.97). Duplicates in Ukrainian notes are near-verbatim rephrasings, so a high threshold works. *Decision:* 0.96.
- **End-to-end on gold text (gemma3:12b)**: 0.603 notes fully correct (target ≥0.6), 0.643 items. Per field: found 0.976, type 0.94, title 0.929, start 0.905, project 0.774, incomplete flag 0.964. Failure causes: (1) project-label ambiguity (largest); (2) note-level dates copied to sibling items ("їдемо у Львів… забронювати готель" gets the trip date), which is debatable; (3) strict title metric marks valid paraphrases as wrong ("Закинути гроші на телефон" vs "Поповнити телефон"); (4) true errors: "Дедлайн по курсовій 15 грудня" not split out as an item, "на одинадцяту завтра" lost its time, "за два дні до того" resolved wrong. *Evidence:* `eval/results/e2e_text.md`.
- **Live API test**: text → 3 items in ~25 s (C4 runs one call per item, sequentially, and dominates). Follow-up answer "в суботу о другій" filled the missing date. Audio path tested with the macOS Ukrainian TTS voice (Lesya): Parakeet heard "лабораторно" instead of "лабораторну"; both dates were correct, including "а ввечері", which inherited "завтра". New C4 error seen: the name "Оля" was normalised to a different name, "Олена".
- **Smoke test (qwen3:8b)**: the walkthrough note produced the correct task and event (Thu 15:00, Андрій, Курсова). Seen errors: "Купити молоко" not linked to "Дім" (threshold too strict), and "Зустріч з ними треба перенести" classified as a task, so no follow-up question was asked.
- **C1 ASR (Parakeet TDT v3)**: on 62 owner recordings, WER 0.182, CER 0.098, name/date-word recall 0.761, 0.21 s/note; C2 normalizer doesn't change WER (0.184). WER overstates errors: digits vs number words ("1 грудня" vs "Першого грудня") and the speaker's own paraphrases count as errors. Real errors are English terms ("NLP" → "Нолпі", "бекенд" → "бакет") and Russian-form numbers ("семь", "ноль"). *Evidence:* `eval/results/c1.md`.
- **End-to-end on the owner's audio (gemma3:12b)**: 0.508 notes fully correct (text: 0.603), 0.536 items (text: 0.643). Per field, audio vs text: found 0.905/0.976, type 0.845/0.94, title 0.786/0.929, start 0.798/0.905, project 0.702/0.774, incomplete 0.893/0.964. So ASR costs about 10 points end to end. Typical ASR-caused failures: a merged time phrase ("в четвер-третій") made C3 drop the event; a mis-heard name pair ("з олою морком" for "з Олею і Марком") broke people/title; a word lost at the start of a sentence led to a wrong type. *Evidence:* `eval/results/e2e_audio.md`.
- **Model comparison gemma3:12b vs qwen3:14b (gold text)**: E2E notes fully correct is a tie, 0.603 vs 0.603 (items 0.643 vs 0.667). qwen is better at C6 project choice (0.869 vs 0.798), C3 segmentation F1 (0.976 vs 0.964) and speed (2.9 vs 3.9 s/note in C3). gemma is better at C3 type macro-F1 (0.978 vs 0.963), C4 people F1 (0.907 vs 0.833) and title match, and much better at C7 recall (0.875 vs 0.5): qwen does not set `unresolved_person` for pronoun-only items, so the C7 rule never fires. *Decision:* keep gemma as the default, because hidden "didn't ask" errors are worse than visible project errors; a hybrid (qwen for C6) is a possible next step. *Evidence:* `eval/results/*_qwen3-14b.md`.
- **Eval tooling fix**: result files of a non-default model now get a model suffix. The first qwen C3 run overwrote `c3.md`; it was renamed, and gemma's C3 was regenerated from its cache.

## Deployment
- **Local deployment**: FastAPI backend (`uv run inbox-server`) + Gradio dashboard at `/ui` + a SwiftUI `MenuBarExtra` app (`macapp/`) that records 16 kHz WAV and posts it to `/notes`. Calendar export is `.ics` instead of the Google Calendar API. *Why:* `.ics` opens in any calendar and needs no OAuth or Google account, which fits the local-only rule.
- **Gradio replaced by a custom board; global hotkey**: the owner found the Gradio dashboard hard to use and dated. It was replaced by a single-page board (vanilla HTML/CSS/JS served by FastAPI, English UI, yellow gradient theme). Items are grouped like a Notion board by type / project / date bucket / status; dragging a card between columns PATCHes the field. The menu-bar app got a system-wide ⌃⌥Space hotkey (Carbon `RegisterEventHotKey`, no accessibility permission) with sound feedback. Gradio is kept only for the full eval reports (`/ui`). *Why:* the user records notes while in other apps, so capture has to be one keystroke, and the inbox must be scannable by project. *Evidence:* `inbox/web/`, `macapp/Sources/VoiceInbox/HotKey.swift`.
- **Board v1 rejected → editorial v2**: the owner found the yellow-gradient board "too acid". v2 follows an editorial newsletter style: off-white page, a rotating public-domain landscape painting as the hero (6 CC0 works from The Met Open Access, downloaded once by `scripts/fetch_art.py`, so the page stays offline), a yellow serif title, vertical italic date and time, italic serif section labels, round checkboxes, and a yellow starburst record sticker. It has a Brief view (sections) and a Board view (columns with drag & drop), with the same grouping logic. The Mac popover was restyled in the same language (system serif italic, starburst button). *Why:* the owner will use it daily; calm typography reads better than saturated colour. *Evidence:* `inbox/web/`, `report/claude_design_prompt.md`.
- **C9 Daily Brief ("The Voice Inbox Gazette")**: a new component that writes a morning newspaper from the stored items: headline, lede, today's agenda, a dispatch per project, a plan of the day, and items awaiting an answer. The LLM refers to items only by id, and rule guards drop unknown ids, done items and dispatches for projects without open items; project membership comes from the store. The first live run showed why: gemma wrote dispatches for all 6 projects, including empty ones, and quoted raw ids ("#10"), which are now replaced by titles. Eval c9 on 3 synthetic inboxes built from gold items: raw invalid-id rate 0.0, raw done-in-agenda 0.0, raw empty-dispatch rate 0.133 (removed by the guard), due-today coverage 0.917, ~44 s per edition (cached once per day). The UI is board-only now; the hero caption links to today's edition instead of a generic summary line. *Evidence:* `inbox/brief.py`, `inbox/prompts/brief.md`, `eval/results/c9.md`, `/gazette`.
- **Main page gets the gazette's newsprint look**: at the owner's request, the board keeps its layout but borrows the Gazette's style: grey newsprint paper with grain, Playfair Display / Libre Caslon type, a blackletter wordmark, double rules and a mono dateline, a muted (sepia-toned) hero painting, a boxed capture panel and ink-ruled columns with small-caps card titles. CSS-only, so behaviour is unchanged. *Evidence:* `inbox/web/styles.css`.
- **Architecture page (`/architecture`)**: a one-page explainer in the Gazette style, linked from the board header. It shows the C1–C9 pipeline with the headline metric per component, one example note traced through every step, the gemma vs qwen comparison, and known failure modes. It is used as the architecture slide in the video. *Evidence:* `inbox/web/architecture.html`.
- **Recent notes with live status**: the owner could not see what happened to a note after recording it, especially from the menu-bar hotkey. The pipeline now reports its stage through an `on_stage` callback (transcribing → cleaning → splitting → reading item n of N → saving). The server keeps the in-progress notes in memory and shows failed ones with their error. `GET /notes/recent` returns these plus the latest stored notes. The board shows a "Recent notes" list under the capture panel; clicking a note highlights its items. *Evidence:* `inbox/pipeline.py`, `inbox/server.py`, `inbox/web/app.js`.
